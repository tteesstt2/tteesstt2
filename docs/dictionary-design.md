# 검색 사전 설계

관련 문서: [검색 처리 설계](./search-design.md)

검색어의 단어를 "무엇을 뜻하는지"로 바꿔주는 사전. 검색 품질의 대부분이 여기서 결정된다.

## 1. 사전 종류

| 사전 | 역할 | 예 |
|---|---|---|
| 장소 사전 | 단어 → 특정 장소 | 센소지 → 浅草寺 |
| 브랜드 사전 | 단어 → 체인점 (여러 지점) | 이치란 → 一蘭 (전 지점) |
| 지역·역 사전 | 단어 → 지역 / 역 | 시부야 → 渋谷区, 渋谷駅 |
| 태그 사전 | 단어 → 장면 태그 | 야경 → night + viewpoint, 비 → rain |
| 품목 사전 | 단어 → 음식·물건 (다국어) | 라멘 → ramen, ラーメン |
| 불용어 | 검색에서 무시할 말 | 추천, 브이로그, 맛집(가벼운 가중치) |

## 2. 사전 항목 구조

```json
{
  "term": "시부야",
  "normalized": "시부야",
  "language": "ko",
  "target_type": "region",
  "target_id": "region_jp_13_shibuya",
  "canonical": "渋谷",
  "weight": 1.0,
  "source": "auto_transliteration",
  "status": "approved",
  "created_at": "2026-09-25"
}
```

| 필드 | 설명 |
|---|---|
| `term` / `normalized` | 원래 표기 / 정규화 표기 (가나 통일, 소문자, 공백 제거) |
| `target_type` | `place / brand / region / station / tag / item / stopword` |
| `target_id` | 연결 대상. 한 단어가 여러 대상일 수 있음 (신주쿠 = 지역 + 역) |
| `weight` | 해석 확신도. 흔한 단어일수록 낮게 |
| `source` | 어디서 왔는지 (아래 3번). 품질 추적용 |
| `status` | `approved / pending / rejected`. 자동 생성 항목은 `pending`에서 시작 가능 |

## 3. 어디서 채우나 (자동 → 사람 순)

### ① DB에서 자동 생성 (항상)
- Place, PlaceName의 모든 이름을 장소 사전으로
- Place의 도도부현·시구정촌·동네·역 값을 지역·역 사전으로
- 장소가 검증·수정되면 바로 반영

### ② 공개 데이터로 초기 적재 (시작할 때 한 번 + 주기적 갱신)

| 데이터 | 가져올 것 | 비고 |
|---|---|---|
| Wikidata | 관광지·역·지역의 ja/ko/en 이름과 별칭 | 한국어 관용 표기 확보에 유용 (CC0) |
| OpenStreetMap | `name`, `name:ko`, `name:en`, `name:ja-Hira` | ODbL 라이선스 표기 필요 |
| 일본 행정구역·역 목록 | 도도부현, 시구정촌, 역 이름·읽기 | 공개 데이터 사용, 라이선스 확인 |

### ③ 규칙으로 표기 변형 생성

| 변환 | 방법 | 예 |
|---|---|---|
| 한자 → 가나 읽기 | 일본어 형태소 분석기(Sudachi 등) 또는 Wikidata 읽기 | 浅草 → あさくさ |
| 가나 → 로마자 | 변환 라이브러리 | あさくさ → asakusa |
| 가나 → 한글 | 규칙 변환 + **관용 표기 변형 함께 생성** | つ: 쓰/츠, じゅ: 주/쥬 → 쓰키지/츠키지, 신주쿠/신쥬쿠 |
| 장음·띄어쓰기 | 변형 생성 | 도쿄/토쿄, 오사카성/오사카 성 |

> 한국 사용자는 국립국어원 표기(쓰키지)보다 관용 표기(츠키지)를 더 많이 쓰는 경우가 있어서 두 가지를 모두 넣는다.

### ④ Gemini로 후보 생성 → 관리자 승인
- 장소 검증 시 "이 장소를 한국인이 부르는 이름·줄임말·별명" 후보 생성
- 예: 浅草寺 → 센소지, 아사쿠사 절, 아사쿠사 사원
- `status: pending`으로 저장 → 관리자 화면에서 승인/반려

### ⑤ 검색 기록으로 보강 (운영 중 계속)
- **결과 0건 검색어** 목록 → 관리자가 사전 항목 추가
- **다시 검색한 기록** (A 검색 → 바로 B로 고쳐 검색 → B에서 클릭) → A를 B의 별칭 후보로 제안
- 주 1회 검토

### ⑥ 태그·품목 사전은 사람이 먼저 만든다
- 장면 태그 목록(약 100~200개)을 먼저 정하고 태그마다 ko/ja/en 동의어를 직접 입력
- Gemini로 동의어 후보를 늘린 뒤 사람이 검토

```json
{ "tag": "night",
  "ko": ["밤", "야경", "저녁", "밤거리"],
  "ja": ["夜", "夜景", "ナイト"],
  "en": ["night", "night view", "evening"] }
```

## 4. 검색할 때 사전을 쓰는 방법

1. **정규화**: 검색어와 사전을 같은 규칙으로 정규화
2. **조사 떼기**: "시부야에서", "라멘집을" → 시부야, 라멘집 (한국어 형태소 분석기 또는 조사 목록)
3. **가장 긴 일치 우선**: "시부야스카이" → `시부야 스카이`(장소) 우선, `시부야`(지역) 후순위. 띄어쓰기 없는 검색어도 처리
4. **여러 뜻이면 모두 보관**: 신주쿠 → 지역 + 역 모두 가산점 (weight로 비율 조정)
5. **사전에 없으면**: 키워드·오타 허용·의미 검색에 그대로 맡김 (해석 실패해도 검색은 됨)

## 5. 관리

| 항목 | 방법 |
|---|---|
| 저장 | DB 테이블 (`search_terms`). 검색 서버는 메모리에 올려 사용, 변경 시 갱신 |
| 관리 화면 | 검색·추가·수정·승인, 출처별 필터 |
| 품질 검사 | 한 단어가 너무 많은 대상에 연결되면 경고 (예: "공원") |
| 테스트 | 사전 변경 시 테스트 검색어 세트로 결과 비교 |

## 6. 시작 순서

1. 태그·품목 사전 초안 (사람, ~200개)
2. 일본 지역·역 공개 데이터 적재
3. Wikidata/OSM에서 주요 관광지 이름 적재
4. 표기 변형 규칙 적용 (가나·로마자·한글)
5. 운영 시작 후 검색 기록 기반 보강

## 7. 직접 쌓지 않고 가져올 수 있는 데이터

| 무엇 | 출처 | 얻는 것 | 주의 |
|---|---|---|---|
| 다국어 이름·별칭 | Wikidata 라벨·별칭 | 浅草寺 ↔ 센소지 ↔ Senso-ji | CC0, 자유 사용 |
| 별칭 (사람들이 부르는 이름) | 한국어·일본어 위키백과 **넘겨주기(redirect)** 목록 | "아사쿠사 절" → 센소지 문서 | CC BY-SA, 덤프 파일 사용 |
| 지명·역 | OpenStreetMap, 일본 행정구역·역 공개 데이터 | 이름, 읽기, 좌표 | 라이선스 표기 |
| 한국인이 실제로 쓰는 표기 | 일본 여행 브이로그 **제목·설명·태그** (YouTube Data API) | 츠키지 vs 쓰키지 중 무엇이 많이 쓰이나 | 이미 수집하는 데이터 |
| 표기 빈도 비교 | 네이버 검색 API (블로그 결과 수), 네이버 데이터랩 | 변형 표기 중 대표 표기 선택 | 공식 API만 사용 |
| 인기 검색어·연관어 | Google Trends, 네이버 데이터랩 | 어떤 장소를 많이 찾는지, 우선 정비 대상 | 목록이 아닌 추이 위주 |
| **영상 속 이름 짝** | 우리 분석 결과: 음성 "이치란" + 간판 "一蘭"이 같은 장면 | 한국어 ↔ 일본어 별칭 쌍이 자동으로 생김 | 영상이 늘수록 저절로 늘어남 |
| 동의어·뜻 | 임베딩 모델, Gemini (웹 전체로 이미 학습됨) | "절 ≈ 사찰 ≈ temple" | 의미 검색이 이미 활용 |

사용하지 않는 것: 구글 자동완성·구글 지도·트립어드바이저 등의 스크래핑 (약관 위반).

**직접 쌓아야만 하는 것**: 우리 검색 결과에 대한 사용자 클릭 기록. 순위 학습에 필요하며 외부에서 구할 수 없다.
